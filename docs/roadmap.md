# Roadmap

Сервис заказов, в котором главная задача — не CRUD, а консистентность: что происходит,
когда два клиента одновременно покупают последнюю единицу товара.

Порядок работы над проектом выбран намеренно: сначала пишется наивная реализация,
затем гонка воспроизводится нагрузочным скриптом, и только после этого чинится —
двумя разными способами, с замерами и сравнением. Такой порядок сохраняет в истории
репозитория и сам баг, и его починку.

**Стек:** Python, FastAPI, PostgreSQL 16, SQLAlchemy 2.0, Alembic, Docker Compose, pytest.

**Вне скоупа:** категории, корзина, скидки, доставка, платёжные интеграции.
Три сущности — `products`, `orders`, `order_items` — и ничего сверх этого.

**Статусы:** ✅ готово · 🔧 в работе · ⬜ запланировано

## M1 — Скелет и инфраструктура 🔧

Postgres в Docker, FastAPI с `/health`, модели SQLAlchemy и одна обратимая миграция.
Бизнес-логики на этом этапе нет.

- [ ] Репозиторий, `.gitignore`, `.env.example`, виртуальное окружение
- [ ] `docker-compose` с `postgres:16`, named volume, healthcheck через `pg_isready`
- [ ] Конфигурация на `pydantic-settings`, секреты только из `.env`
- [ ] Подключение к БД: `create_engine`, `sessionmaker`, `DeclarativeBase`, зависимость FastAPI через `yield`
- [ ] Модели в стиле SQLAlchemy 2.0 (`Mapped`, `mapped_column`, `__table_args__`), `naming_convention` у `MetaData`
- [ ] Alembic: URL и metadata из настроек, функция и триггер через `op.execute`, рабочий `downgrade`
- [ ] `GET /health` с реальным запросом в базу

**Критерий закрытия:** `alembic upgrade head` → `downgrade base` → снова `upgrade head`
проходят без ошибок, `\d order_items` совпадает с `docs/schema.md`, паролей нет ни в коде,
ни в истории гита.

## M2 — CRUD по товарам ⬜

Слои `router → service → repository` на простом CRUD — структура, которая
переиспользуется на всех следующих этапах.

- [ ] Pydantic-схемы запросов и ответов, отдельно от моделей БД
- [ ] Репозиторий товаров: create, get, list, update
- [ ] Сервисный слой без знания про FastAPI
- [ ] Роутер `/products` с корректными кодами ответов
- [ ] Обработка ошибок: 404, 409, валидация
- [ ] Пагинация списка

**Критерий закрытия:** роутер не содержит ни одного запроса к БД, сервис — ни одного `HTTPException`.

## M3 — Создание заказа, наивная версия ⬜

Заказ создаётся «в лоб»: прочитать остаток → проверить → вычесть → записать.
Реализация заведомо некорректна под конкурентной нагрузкой, и это часть плана.

- [ ] `POST /orders` с несколькими позициями
- [ ] Снимок цены в `order_items.unit_price`
- [ ] Подсчёт `total_amount`
- [ ] Проверка и списание остатка
- [ ] `GET /orders/{id}`

**Критерий закрытия:** заказ корректно создаётся при последовательных запросах.
Блокировки на этом этапе не добавляются.

## M4 — Воспроизведение гонки ⬜

Нагрузочный скрипт, который параллельно покупает последнюю единицу товара
и ломает наивную реализацию.

- [ ] Скрипт на N параллельных запросов к одному товару
- [ ] Зафиксированный оверселл: остаток уходит в минус либо заказов создаётся больше, чем товара
- [ ] Вывод скрипта сохранён в `docs/` для README
- [ ] Разбор: при каком уровне изоляции это происходит и почему

**Критерий закрытия:** баг воспроизводится стабильно, а не эпизодически.

---

## M5 — Починка двумя способами ⬜

Пессимистичная блокировка против оптимистичной, с замерами на одном и том же скрипте.

- [ ] Вариант A: `SELECT ... FOR UPDATE`
- [ ] Вариант B: колонка `version` и retry при конфликте
- [ ] Прогон скрипта из M4 на обоих вариантах — оверселла нет
- [ ] Замеры времени и количества отказов, сведённые в таблицу
- [ ] Разбор deadlock: при каком порядке захвата блокировок он возможен
- [ ] Выводы в `docs/locking.md`

**Критерий закрытия:** для каждого варианта сформулировано, при какой нагрузке он выгоднее.

---

## M6 — Идемпотентность создания заказа ⬜

Повторный запрос с тем же `Idempotency-Key` не создаёт второй заказ.

- [ ] Хранилище ключей идемпотентности с UNIQUE-ограничением
- [ ] Заголовок `Idempotency-Key` в `POST /orders`
- [ ] Повтор возвращает тот же заказ — не дубль и не 409
- [ ] Поведение при двух одновременных запросах с одним ключом
- [ ] TTL ключей
- [ ] Тест на дубликат

**Критерий закрытия:** два параллельных запроса с одним ключом дают ровно один заказ.

## M7 — Статусная модель и отмена ⬜

`created → paid → cancelled`: переходы валидируются, отмена транзакционно возвращает
остаток на склад.

- [ ] Enum статусов и таблица допустимых переходов
- [ ] `POST /orders/{id}/pay`, `POST /orders/{id}/cancel`
- [ ] Запрет недопустимых переходов
- [ ] Возврат остатка в той же транзакции, что и смена статуса
- [ ] Гонка: одновременные отмена и оплата
- [ ] Тесты на все переходы
